# Сверка правового основания в очереди рекламы

Реализовано 19 октября 2026. Публикация нового API и Hosting — отдельно.
Это сверка кандидатов с явным решением аналитика, не автоматический вывод
о законности и не постоянный белый список ЖК.

## Проверенные публичные источники

Проведены ограниченные HTTP-чтения из среды разработки без Gemini/SearchAPI.
Homeportal вернул каталог и отдельные карточки ВКО с разрешениями МИО и
гарантиями КЖК. Публичный frontend использует API
`https://api.homeportal.kz/api/v1/`: POST `getobjects` и GET `objects-detail/{id}`.
В каталоге регион ВКО имеет id 16, город Өскемен — 73; поиск названия не заменяет
городской фильтр. Для адаптера задан регион 16, первая страница строящихся объектов.
Результат может не охватить старое название, завершённый объект или другую очередь.
Отсутствие совпадения **не означает** отсутствие основания.

В detail использованы тип основания, номер, дата выдачи, объект/адрес,
застройщик и уполномоченная компания с БИН. Тип 1 — разрешение МИО, 2 — гарантия.
Банковское финансирование (тип 3) этим действием не подтверждается.
Достоверного поля отмены/текущего срока действия не обнаружено:
аналитик проверяет оригинал и действие документа на дату рекламы отдельно.
Дата ввода дома **не является** датой истечения разрешения.

[Ashyq Data](https://ashyq.data.gov.kz/dataset/magda-ds-b80110e9-218a-42ba-b8c8-01fa5e4c82c8)
раскрывает полную CSV-выгрузку в `s3.sdu.gov.kz/magda-datasets/miir_kazreestr_du_objects/`.
Получено 4005 строк (около 1,2 МБ). Фактические поля:
`id, object_name, builder_name, auth_org_name, address_name, date_start, date_end,
number, time_modif, sdu_load_date`. **БИН в этой выгрузке нет**, несмотря на описание
метаданных. Встречаются разные виды реквизитов, включая гарантийные.
Наблюдаемый `sdu_load_date` — 2026-06-15: время загрузки страницы каталога
не делает эти строки актуальными на октябрь. UI сохраняет дату строки;
подтверждать основание прямо по CSV нельзя. Метаданные набора указывают
Creative Commons Attribution 3.0 New Zealand; источник указан в карточке и здесь.
Семей/область Абай исключаются из адресного фильтра, даже при старой пометке ВКО.

E-License: публичная страница поиска открылась, но есть CAPTCHA — только ручная
проверка, без обхода. Qazreestr: главная открылась; полный анонимный поиск текущих
разрешений не подтверждён. Остальные ссылки организаторов остаются справочными.
Реальные выгрузки, контакты и карточки не включены в репозиторий или тесты.

## Действия в приложении

1. Мониторинг → находка → «Сверить разрешение или гарантию».
2. Ввести название ЖК/адрес; поиск запускается только кнопкой. Источники отвечают
   независимо: отказ одного не превращается в пустой результат другого.
3. Для Homeportal открыть «Проверить документ», сверить оригинал по ссылке.
4. Указать проверенную дату рекламы. Известная дата публикации фиксирована;
   при неизвестной нужно проверить оригинал вручную. Начало кампании Meta и дата
   получения не подставляются вместо даты публикации.
5. Подтвердить объект, блок/очередь, получателя/БИН, действие/отсутствие отмены,
   дату рекламы и отсутствие иных нерешённых оснований для проверки. Добавить
   обоснование. Если есть другие риски, оставить находку в работе.
6. Сохранить: сервер повторно читает карточку; документ, выданный после рекламы,
   отклоняется. Контрольная сумма значимых полей связывает решение с просмотренным документом;
   изменение реквизитов требует новой сверки. Версия/связь с ЖК/AI проверяются
   повторно атомарно перед записью.
   Находка становится `dismissed`, остаётся в «Все находки» и истории.

По умолчанию очередь показывает серверный фильтр `active` (`new` + `investigating`)
со стабильной пагинацией. Никакие баллы, факторы или карточки ЖК это действие
не меняет. Для уже переданной в ЖК находки основание проверяется в карточке ЖК.
Повторное открытие находки снимает текущее подтверждение, сохраняя прежнее в аудите.
Изменённый текст рекламы получает отдельную ревизию без переноса подтверждения.
Повторное обнаружение отложенной находки не включает её в авто-AI.

## Контракты и ограничения

Все новые endpoints требуют прежнюю роль аналитика/администратора:

- `GET /api/v1/monitoring/items/{id}/registry?q=...` — кандидаты двух источников;
- `GET /api/v1/monitoring/items/{id}/registry/{homeportalNumericId}` — документ;
- `POST /api/v1/monitoring/items/{id}/basis-review` — expectedVersion, expectedDocumentSha256, recordId,
  advertisementDate, objectMatches/phaseMatches/holderMatches/
  documentValidityChecked/advertisementDateChecked/otherRisksReviewed (все true), notes.

MonitorItem получает необязательное `basisReview` (старые записи совместимы):
документ с исходной ссылкой, SHA-256 ответа, временем запроса и реквизитами;
дата рекламы, автор/время/обоснование решения. Событие `item.basis.confirm`
содержит тот же снимок; UI скрывает UID через ActorName, аудит сохраняет автора.
Контакты компаний, необработанный ответ и персональные поля не возвращаются.

Только фиксированные HTTPS-адреса, без редиректов, максимум 2 МБ/ответ,
ограниченное время, 20 кандидатов/источник, без пагинации внешнего API и повторов.
Общая квота проекта — 100 операций поиска/detail/подтверждения за сутки UTC
в `monitorLimits/registry-YYYYMMDD`. Публичный CSV кэшируется на 5 минут на процесс;
detail при подтверждении читается заново. Правила доступа не меняются.
Существующий индекс monitorItems(status ASC, createdAt DESC, __name__ ASC)
поддерживает новый IN-фильтр. Новые коллекции/ключи/env не требуются.

Проверки интеграции в тестах используют только явно синтетические MockTransport
и локальный Firestore emulator. Это не облачная приёмка. После выпуска вручную
проверить разрешение и гарантию, идентичность очереди/получателя и исходный
документ; убедиться, что активная очередь скрывает подтверждённую находку,
«Все находки» и аудит сохраняют её. Веб-каталог не гарантирует полноту,
юридическую применимость или актуальность реестра.

## Продолжение публикации

После зелёного CI/review взять SHA этого PR, обновить исходники в Cloud Shell.
Собрать backend по существующему `deploy/cloudbuild.yaml`, обновить только image
действующего сервиса (сохранив env/secrets/SA/лимиты), затем собрать frontend с
прежней проверенной Hosting-конфигурацией и выполнить `firebase deploy --only hosting`.
Обновить образ worker тем же проверенным image по текущей инструкции мониторинга;
не включать новый авто-AI/поиск и не менять Scheduler при этом.
Новые ключи, IAM/rules и индексы не добавляются. Сначала API, потом Hosting:
старый frontend совместим с новым сервером, новый ожидает registry endpoints/active.
