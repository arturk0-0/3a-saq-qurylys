# Мониторинг публичных публикаций

MON-01–08 реализованы в feature-ветке; включение расписания/новых индексов и
облачная приёмка — отдельный MON-09. [Результаты проверок](monitoring-report.md).
Instagram KZ добавлен через **SearchAPI / Meta Ad Library** и проверен двумя
настоящими поисками, остаток 98/100. [Контракт, резерв 20 и trial](instagram-searchapi.md).
Настройка ключа/разрешение на сервере и cloud rollout — отдельные действия;
[ограничения прямого доступа](instagram-feasibility.md) сохраняются.
Интернет-поиск не заменяет библиотеку рекламных показов.

## Как пользоваться

1. Войти как analyst/admin → «Мониторинг рекламы» → «Источники сбора».
2. Выбрать Instagram / Meta Ad Library (SearchAPI), интернет-поиск либо публичный
   Telegram-канал. Сохранить запрос с городом/словами о жилье либо имя канала
   (`@channel` или `https://t.me/channel`). Не нужно вводить ссылку каждого поста.
   Авто-AI по умолчанию выключен. Включение означает платные запросы Gemini.
3. Нажать «Получить публикации». История показывает прочитанные/отфильтрованные/новые/
   повторные материалы и ошибки. Интервал обязателен и для ручного повторного сбора.
4. В очереди открыть находку, исходную ссылку и контекст. Проверить текст, дату,
   регион и актуальность. Поисковый фрагмент не является полным оригиналом.
5. При необходимости явно запустить платный AI-анализ. Вывод — только гипотеза
   R2/R3, не юридическое заключение. Решение «В работу/Отложить/Вернуть в очередь»
   с обоснованием меняет очередь, а не факторы или баллы.
6. При наличии проверенного **реального** ЖК и разрешённого реального workspace
   передать публикацию в его карточку. Сохранённый AI-результат переносится без
   нового Gemini-вызова как proposed evidence/hypotheses. Далее прежний путь:
   проверка источника → отдельное решение R1–R6 → сигнал → решение → PDF.
   В DEMO-only окружении привязка реальной находки заблокирована.

Реальные ЖК не создаются автоматически из названия публикации. Приложение пока
не предоставляет отдельного UI их provisioning: это административный процесс
с проверкой исходных документов. Нельзя отключать DEMO-only ради демонстрационной
привязки к вымышленному seed. Выбор в UI ограничен первой сотней доступных ЖК;
если нужного нет, нельзя выбирать похожий.

## Что именно собирается

- `instagram_ads`: один поиск Meta Ad Library через SearchAPI, KZ/Instagram/active/all.
  Это объявления, а не Google SERP. Текст, ID, начало показа, платформы и ссылки
  на материалы; до 30 карточек, без пагинации. Медиа-only без текста пропускаются
  с явным unreadable count. [Отдельные лимиты и квоты](instagram-searchapi.md).

- `web_search`: фиксированный HTTPS Bing RSS endpoint. Сохраняется выдаваемый
  поиском текст title/description как `search_snippet`, ссылка обнаружения и
  исходная ссылка результата. Переход/загрузка произвольного результата не выполняется.
  Операторы запроса и полнота индекса зависят от поисковика; выдача иногда
  нерелевантна. `site:instagram.com` не гарантирует Instagram-результат.
- `telegram`: фиксированный HTTPS `t.me/s/{channel}`. Только последнее доступное
  окно публичных текстовых постов, до 30. Не подписка на все каналы, не полный
  архив и не выгрузка изображений/видео. Канал выбирает команда.
- В очередь попадают тексты со словами региона ВКО **и** жилья. Найденные слова
  показаны отдельно. Алгоритм может пропускать рекламу без города, включать
  нерекламные новости/вторичное жильё; слова об оплате не подтверждают R2.
- Недоступность/403/429, нераспознанная HTML-страница и успешная пустая RSS-выдача —
  разные состояния. «Находок нет» не означает «рекламы нет».
- Изображения, Stories, закрытые профили, неизвестные Telegram-каналы и
  персональная история показов и полный таргет Instagram не входят в этот охват.
  Поставщик возвращает доступные рекламные карточки библиотеки, не все показы.

Исходные URL нормализуются (убираются tracking query/fragment), но оригинальные
смысловые параметры сохраняются. `id=SHA256(normalizedUrl + ":" + textSha256)`;
`revisionKey=SHA256(normalizedUrl)` связывает разные тексты одной ссылки.
Повтор сохраняет решения эксперта, обновляет только lastSeenAt/sourceIds.
Изменённый текст — новая неизменяемая находка. Сравнение ревизий в UI не реализовано.
Для Instagram fingerprint также учитывает kind/path media reference без
подписи query/CDN host; это не hash содержимого медиа.
Хранятся точный полученный текст, SHA-256 текста и ответа источника, URL,
тип/аккаунт/даты. Ответ HTML/RSS целиком не сохраняется — его hash не позволяет
восстановить страницу и сам по себе не является заверенной копией рекламы.
Неизвестное publishedAt остаётся null, capturedAt/createdAt не подменяет его.

## Доступ, данные и API

Все `/api/v1/monitoring/*` требуют Firebase ID token и analyst/admin.
Клиентские Firestore rules остаются deny-all; worker работает через закрытые ADC.
Очередь общая для аналитиков проекта, не пользовательское/публичное хранилище.
Публикации — реальные наводки, коллекции отделены от DEMO workspace. Остальные
контракты продолжают применять прежний DEMO scope.

| Коллекция | Назначение |
| --- | --- |
| monitorSources | Запрос/канал, интервал, enabled, autoAnalyze, version, lease |
| monitorItems | Неизменяемое содержимое находки, provenance, решение, AI, ad link |
| monitorRuns | Состояние/счётчики/ошибка отдельного сбора |
| monitorEvents | Аудит настроек источника, решений и AI без endpoint изменения |
| monitorLimits | Число источников, дневные fetch-резервы, heartbeat worker |
| monitorAiRuns | Идемпотентный AI requestId, статус, модель/prompt/hash/результат |
| usageLimits | Общие с прежним анализом global/user дневные AI-счётчики |

- `GET /status` — heartbeat (не гарантия будущих запусков), fetch-квота,
  `liveRegistryEnabled`, `instagramTargetedAds=not_connected|configured` (настройка,
  не live health), searchApi dailyUsed/dailyLimit/creditReserve,
  creditsObservedBefore/checkedAt/unsettledAttempts. Status не вызывает поставщика.
- `GET/POST /sources`; POST: name, kind, target, intervalMinutes, autoAnalyze.
  Дубли kind/target возвращают существующий источник, не сбрасывают opt-in.
- `PATCH /sources/{id}`: expectedVersion, enabled, autoAnalyze.
  Target/interval в первой версии неизменяемы. Удаления нет; пауза не освобождает
  слот из 20 источников. Другой запрос создаётся отдельным источником.
- `POST /sources/{id}/run` — один bounded сбор, не запуск постоянного scheduler.
- `GET /items?status=&cursor=&limit=`, `GET /items/{id}`,
  `GET /items/{id}/history`, `GET /runs?cursor=&limit=`.
  Страницы newest-first createdAt DESC, __name__ ASC, cursor=ID.
- `POST /items/{id}/review`: expectedVersion, decision=new|investigating|dismissed,
  notes. Actor/date — серверные, запись и аудит атомарны.
- `POST /items/{id}/analyze`: expectedVersion, UUID requestId.
  Повтор requestId не вызывает Gemini снова; UI показывает сохранённый aiStatus.
  Ошибка модели/квоты/JSON не подтверждает гипотезы.
- `POST /items/{id}/attach`: expectedVersion, complexId, notes.
  Только real→real, повторная привязка к другому объекту запрещена.

409 требует явного обновления и пересмотра решения; введённые заметки сохраняются
в UI. Клиент не присылает reviewer и не изменяет score. Неизвестные ошибки
источников не сохраняют body/provider secrets. Текст внешней страницы экранируется.

## Лимиты и регулярный worker

До HTTP-запроса транзакционно резервируются запуск, дневная fetch-квота и
10-минутный lease источника. Смена владельца lease проверяется при каждой записи
и завершении: старый процесс не перезаписывает новый запуск.
Повторный запуск после истечения lease/интервала отмечает оставленный running
run как failed/MONITOR_LEASE_EXPIRED. Исходники сортируются по сроку следующего
запуска; ограниченная batch не закреплена за первыми ID.

Общие/public лимиты по умолчанию: максимум 20 источников, 30 наблюдений/ответ,
1.5 MB **распакованного**
body, connect timeout 4 s, read 12 s, общий контроль потока 20 s
(проверяется между chunks; возможна добавка read timeout). Redirects не выполняются.
`MONITOR_DAILY_FETCH_LIMIT=100`, `MONITOR_SOURCES_PER_TICK=3`.
Квота UTC учитывает неудачные запросы тоже; это ограничение операций, не денег.
Для SearchAPI отдельные 2 MB/read 80 s, общая provider lease, дневной cap 2,
reserve >=20 и консервативный pending ledger; расписание opt-in выключено.
Подробная процедура восстановления неизвестных search исходов —
[instagram-searchapi.md](instagram-searchapi.md#зависшиенеопределённые-попытки).

Auto-AI выключен по умолчанию; после явного включения — максимум **одна**
ещё не анализировавшаяся находка на запуск источника. Новые и повторные находки
учитываются, failed автоматически не повторяется. До Gemini резервируются
общие `AI_DAILY_GLOBAL_LIMIT`/`AI_DAILY_USER_LIMIT`. У worker свой service actor;
global quota общая с UI. Лимиты в API и worker должны совпадать.
Прикреплённая публикация анализируется дальше в обычной карточке объявления.
Модель выбирается явно, без автоматического fallback.

Локально из backend с private Firebase ADC и настройками проекта:

```bash
.venv/bin/python -m app.cli.monitor
.venv/bin/python -m app.cli.monitor --watch
```

Первая команда — одна batch due-источников; вторая проверяет их раз в 60 s,
пока процесс жив. Это owner-operated CLI, не публичный auth endpoint.
Обычный Cloud Run HTTP service не гарантирует фоновую работу после ответа.
Для облака нужен отдельный Job/Scheduler:
[порядок активации](cloud-deployment.md#7-мониторинг-job-и-расписание).

## Восстановление после прерывания

Fetch-lease восстанавливается следующим due-запуском после истечения 10 минут
и interval; не сбрасывайте его вручную у ещё живого процесса.
Квоты не возвращаются после неизвестного внешнего исхода.

Если процесс погиб **после AI reservation**, item/monitorAiRuns могут остаться
running. Автоматического снятия этой блокировки нет: неизвестно, списал ли
провайдер оплату/завершил ли генерацию. Не удаляйте run/requestId и не обнуляйте
usageLimits для повторной попытки. Администратор должен:
1. Остановить источник/worker и убедиться, что владелец запроса больше не работает.
2. Приватно сверить item.aiRequestId, monitorAiRuns.id, даты и журналы выполнения
   без публикации текстов/ключей. Сохранить исходные записи/результат расследования.
3. Если поздний успешный результат отсутствует и подтверждена гибель процесса,
   выполнить проверяемую административную транзакцию: прочитать обе записи,
   проверить тот же requestId и running, отметить обе failed с отдельным
   операционным errorCode, увеличить item.version и добавить monitorEvents audit
   с actor/date/reason. Не создавать extraction и не подтверждать факторы.
4. После отдельного осознанного решения возможен **новый платный** requestId.
   Команды самостоятельного восстановления/публичного API здесь нет; это
   ограничение первой версии, а не скрытый автоматический retry.

Код и тестовые адаптеры не доказывают готовность production indexes/IAM/Meta/
Scheduler. Для приёмки проверяется конкретный опубликованный SHA.
