# Единая реклама и автоматический приоритет · два Кодекса

Согласовано владельцем 20 октября 2026. Это план новой реализации, а не отчёт
о готовой функции. База — main `11fd48c` или проверенное более новое продолжение.
Сохранить PR #25–28: компании, карта, дрон, локальный режим, отступы; готовность
строительства/проценты/полосы обратно не добавлять.

## Пользовательский результат

- Один пункт меню «Реклама», ровно две вкладки: «Все материалы» и
  «Источники и расписание». История запусков находится внутри второй вкладки.
- Все материалы: поиск и фильтры необходимости проверки, способа добавления,
  платформы и ЖК. По умолчанию первыми идут требующие проверки, по приоритету.
  Фильтры, сортировка и пагинация выполняются сервером по всей доступной выборке.
- Новый поддерживаемый материал автоматически попадает в очередь анализа.
  Нет основной кнопки «Анализировать». Статусы объясняют ожидание/работу/ошибку;
  повторный запуск доступен только после ошибки, с серверными ограничениями.
- Одна карточка объединяет точные повторы одного рекламного предложения,
  сохраняя все оригинальные публикации, URL, платформы, аккаунты и даты.
  Похожие предложения с иным адресом, ценой или условиями не склеивать молча.
- В одной странице: оригинал/медиа, публикации, ЖК или выбор кандидата,
  гипотезы с цитатами, документы и решение. Нет обязательного перехода между
  находкой, объявлением, доказательством и отдельной панелью факторов.
- У гипотезы: «Подтверждаю / Отклоняю / Недостаточно данных»; общий комментарий,
  одна кнопка «Сохранить проверку». Сервер сохраняет решения, доказательства и
  подтверждённые факторы согласованно, с аудитом и проверкой актуальной версии.
- «Приоритет проверки» — автоматический предварительный показатель для очереди
  материалов/ЖК, с объяснением. «Подтверждённые риски» — прежняя серверная R1–R6.
  ИИ не подтверждает факторы. Ни число дублей, ни уверенность модели сами по себе
  не увеличивают оценку. Неизвестное разрешение не превращается в R1.
- После решения старый дубль не возвращает материал в очередь; действительно
  новая существенная ревизия может требовать новой проверки. История сохраняется.

## B — этот Кодекс / владелец: backend, контракты, интеграция

Ветка `feat/B-materials-auto-priority`.

1. Сначала реализовать зафиксированный additive API из
   [контракта](../material-workflow-contract.md), сохранив старые endpoints/данные.
   Проверить фактические схемы и расширять контракт совместно с A.
2. Объединить доступные мониторинговые находки и ручные объявления единым
   представлением материалов. Связи не теряют оригинальные IDs/историю/файлы;
   существующие записи и решения не требуют разрушительного reseed.
3. Дедупликация с учётом workspace, происхождения, нормализованного содержимого,
   вложений и существенных условий. Безопасная конкурентная обработка. Пропуск
   уже проанализированного неизменённого материала без нового Gemini-запроса;
   результаты разных фото нельзя разделять только по совпадению подписи.
4. Надёжная очередь автоанализа на всех поддерживаемых путях поступления:
   ручной ввод, upload, сбор worker. Lease/идемпотентность/retry/перезапуск,
   существующие квоты и резерв SearchAPI не менять. Изменение текста/вложения
   создаёт новую анализируемую ревизию, поздний ответ не перезаписывает новую.
   При лимите сохранять материал и ожидание; сетевые ошибки не создавать
   бесконечные платные повторы. Не включать реальные платные запросы в разработке.
5. Отдельная детерминированная, объяснимая модель предварительного приоритета;
   формулу и границы уровней зафиксировать/покрыть тестами до интеграции.
   Повтор фактора не суммировать; подтверждённые R1–R6/сценарии 35/70/10 сохранить.
   Отклонённая гипотеза не оживает от дубля. При неопределённом ЖК не приписывать
   баллы похожему объекту; дать возможность выбрать/проверить соответствие.
6. Одна серверная операция review: проверка версии материала/ЖК, роли, допустимых
   решений и достаточности каждого доказательства; атомарность или безопасное
   транзакционное завершение без частично подтверждённых баллов; аудит, конфликт,
   повтор запроса, старый снимок и сигналы/PDF. Нет авто-R1 по пустому справочнику.
7. Текст и загруженные изображения анализировать автоматически в рамках
   существующей поддержки. Отдельно проверить возможности видео: внешняя ссылка
   или превью не равны просмотренному видео. Для неподдерживаемого/недоступного
   формата отдавать явный статус, не выдумывать результат. Дрон и документы
   используют свои контракты; наблюдения дрона не добавляют рекламные R1–R6.
8. Тесты/Ruff/SDK integration/индексы/local-demo, совместная проверка A → B,
   отчёт `docs/unified-advertising-backend-report.md`, план и выпуск. В разработке
   не использовать облачные credentials/платные AI/SearchAPI, не деплоить.

Границы B: `backend/**`, `firestore.indexes.json`, `deploy/**`, `scripts/**`,
контракты и общие план/WORK_LOG. **Не менять frontend A параллельно.** Если для
local-demo нужен frontend shim, согласовать патч с A, не править его молча.

## A — второй Кодекс: весь пользовательский интерфейс

Ветка `feat/A-unified-advertising-ui`.

1. Прочитать новый контракт; создать клиентские типы/адаптер и явно отдельные
   синтетические QA fixtures. Backend может разрабатываться параллельно:
   полноценный UI проверяется на QA API, production не подменять моками.
2. Объединить меню/маршруты мониторинга и объявлений в «Рекламу». Две вкладки;
   перенос старых deep links с сохранением выбранного материала/параметров,
   история запусков внутри настроек. Источники/расписание сохраняют возможности.
3. Список всех материалов, поиск/фильтры/серверная пагинация, ясные статусы
   автоматического анализа, badge повторов и ссылки на ЖК. Не объединять
   страницы старых API и не вычислять серверную фильтрацию на первом экране.
4. Единая карточка проверки: оригинал, переключение публикаций/медиа, гипотезы,
   выбор ЖК/кандидата, сведения о документах, общий комментарий и одна форма.
   Убрать обязательные промежуточные кнопки принятия гипотезы/переходы.
   Подтверждение явно относится к выбранным признакам, не ко всем сразу.
5. Приоритет проверки и подтверждённые риски понятно подписать, серверные числа
   не рассчитывать в браузере. В списках важен предварительный приоритет,
   внутри проверки — подтверждённые факторы и основания. Не показывать «0»
   вместо ещё не выполненного анализа; не называть гипотезу нарушением.
6. Упростить связанные блоки ЖК/сигнала и старые точки входа, сохранив документы,
   историю, приватные загрузки, рекламный след, компании, карту и дрон.
   Основной путь не требует перехода на старый экран; запасные ссылки допускаются.
7. Отступы: общий content-pad 24 px desktop / 18 px mobile, между карточками
   16–24 px; не вкладывать padding дважды. Читаемые заголовки/формы; понятные
   loading/empty/error/conflict/quota/unsupported. Общий CSS без ломания разделов.
   Проверить 1440/375/320 px, keyboard/reduced-motion и отсутствие page overflow.
8. Vitest/typecheck/build и browser QA с тестовыми адаптерами. Отчёт
   `docs/unified-advertising-ui-report.md`, скриншоты, команды и ограничения.
   Маленькие законченные commit/push, отдельный PR. Не merge/deploy самостоятельно.

Границы A: **`frontend/**`**, его QA, только собственный UI-отчёт.
Не менять backend, индексы, seed, auth/rules, deploy, общий план/WORK_LOG/AGENTS
и серверный контракт без согласования с B. Не нужны Cloud Shell, секреты,
платные AI/SearchAPI и ручные действия владельца.

## Порядок совместной интеграции

B публикует контракт → A параллельно строит UI на контракте/QA → B реализует API
и тесты → оба сверяют payload/ошибки → совместный реальный local-demo сценарий
с новым API → review/CI → интеграция → отдельная публикация владельцем.
До готовности B не вливать UI, который обращается к отсутствующим endpoints.
Новый план отменяет историческое разрешение B параллельно менять MON frontend.
Старые MAP/ORG задания не выполнять заново.
