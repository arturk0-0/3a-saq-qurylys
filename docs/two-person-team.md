## Границы файлов

**A пишет:**

- `frontend/**`, включая тесты, статические ресурсы и явно локальный QA runner.
- `docs/frontend-handoff.md` — собственный текущий отчёт/результаты/следующий шаг.
- `docs/demo-scenarios.md`, `docs/judge-runbook.md`, `docs/pitch.md`,
  `docs/demo-checklist.md`, `docs/images/ui-*` — пользовательские материалы.

Тестовые адаптеры остаются в QA. Они не подключаются к обычному frontend/backend
runtime, не отключают настоящий вход и не выдаются за облачную проверку.
Изменения зависимостей — только при доказанной необходимости, без смены стека.

**B пишет:**

- `backend/**`, `data/**`, `deploy/**`, `.github/**`, `scripts/**`,
  `compose.yaml`, Docker/config, Firebase rules/indexes.
- `AGENTS.md`, README/инструкции настройки, `docs/PROJECT_SPEC.md`,
  `docs/DEVELOPMENT_PLAN.md`, `docs/WORK_LOG.md`, архитектуру/API/AI/risk/release docs.

B может объединять согласованные frontend PR и разрешать конфликты интеграции,
но не начинает параллельную переработку дизайна, пока эту задачу ведёт A.
A при серверном дефекте фиксирует шаги и ожидаемое поведение в своём отчёте/PR,
продолжает независимую UI-работу и не меняет API/rules в обход B.
Совместные пользовательские документы B правит только в согласованном review,
чтобы не конфликтовать с очередью A.

## Как не столкнуться двумя Codex

1. Прочитать AGENTS, спецификацию, этот документ, план, отчёт своей роли и
   WORK_LOG. Проверить remote branches, открытые PR и текущее состояние CI.
2. Новую работу начинать от свежего `origin/main`: #6/#7/#11 уже слиты.
   Создать собственную ветку `feat/A-01-ui-final-pass` / `perf/A-02-route-loading`.
   Перед работой проверить, не появились ли новые PR A; не копировать старый UI
   из архивной feature-ветки и не сливать чужие изменения без проверки.
3. В начале задачи отметить её ID и роль в собственном PR/отчёте. A обновляет свой
   hand-off, B — общий журнал/план. Не редактировать одновременно общие файлы.
4. Маленькие законченные коммиты → подходящие проверки → push своей ветки → PR.
   Существующий открытый PR с этим ID сначала прочитать: не создавать дубль.
5. Не force-push main, не заменять чужую работу. После выполнения роли остановиться
   с результатом; новый продуктовый объём вне очереди сначала согласовать.
